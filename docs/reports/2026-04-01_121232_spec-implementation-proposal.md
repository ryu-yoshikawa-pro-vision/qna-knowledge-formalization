# 仕様書整合化に関する提案書

## 1. 背景と課題

`inputs/2026-03-30/spec` は、プロダクトの方向性、業務ルール、状態遷移の骨格は十分に整理されていました。  
一方で、実装開始に必要な契約定義、DB 実体、共通 API、横断ルールには未解消の不整合が残っており、そのまま着手すると次の問題が発生する状態でした。

* 画面と API が 1 対 1 で結び付かず、実装者が都度判断を迫られる
* DB に保存先がない項目があり、仕様通りに動かせない
* 認証、正式取り下げ、コメント統制、通知、検索の挙動が資料ごとにずれる
* 共通ヘッダーや履歴導線など、実利用に直結する導線が閉じていない

これは単なる文言の揺れではなく、着手速度、見積精度、品質保証、運用事故率に直結する課題でした。

## 2. 今回の修正目的

今回の修正目的は、MVP の機能範囲を削らずに、仕様書を「実装判断が不要な状態」まで引き上げることです。

具体的には、次を狙いました。

* API 契約と DB 定義を一致させる
* 共通ヘッダー、履歴導線、レビュー導線などの利用頻度が高い横断機能を閉じる
* 二重送信、再送、再実行時の扱いを固定し、実装と運用の事故を減らす
* 事業側が「何を直したのか」「何が良くなるのか」を説明できる資料にする

## 3. 期待効果

### 実装着手速度の改善

`user_sessions`、`request_comment`、`is_edited`、`search_vector`、`dedupe_key` など、実装に必要な実体を仕様へ補完したことで、設計の持ち帰りや追加確認が減ります。  
結果として、backend / Web / Mobile の並行着手がしやすくなります。

### 正式化プロセスの信頼性向上

`formal -> shared` の正式取り下げ、comment hide 権限、review queue count、permissions DTO を明示したことで、レビュー運用と正式化運用の解釈差を抑えられます。  
これは「誰が何をできるか」が曖昧なまま進むことによる運用事故を防ぎます。

### 検索と再利用性の改善

`searchable_text` と `search_vector` の責務を分離し、merged tag 検索時の解決方法を固定したことで、検索の再現性が上がります。  
ナレッジが見つからない、旧タグで探せない、といった利用初期の不満を抑えやすくなります。

### 参加導線と継続利用の安定化

`relationship_status`、join request コメント保存、cancel ログ、共通ヘッダー API を揃えたことで、初回参加から日常利用までの導線が一貫します。  
導線の分岐ミスや、状態の取り違えによる UX 不整合を減らせます。

### 運用コストの抑制

通知重複抑止、二重送信ルール、既読化や再送の idempotency を明文化したことで、MVP でも運用現場で起こりやすい小さな事故を先回りで防げます。  
これはリリース後の調査工数や問い合わせ対応の削減につながります。

## 4. 実装優先度と投資対効果

優先度は次の順で捉えるのが妥当です。

1. 認証 / 参加 / 共通ヘッダー
2. ナレッジ作成 / レビュー / 正式化
3. 正式ナレッジ改訂
4. Q&A / 履歴 / ナレッジ化
5. 通知 / コメント / リンク / 管理

投資対効果の観点では、最初に効くのは「認証・参加・共通ヘッダー」と「ナレッジ作成・レビュー・正式化」です。  
ここが安定すると、ユーザーは価値の中心である検索、投稿、レビュー、正式化を迷わず使えます。  
一方で、通知重複抑止や履歴導線の補強は、派手ではないものの、継続利用時の信頼性を支える基盤投資です。

今回の修正は、MVP の見た目を増やす投資ではなく、実装遅延と運用事故を減らす投資です。  
そのため、短期的な機能増加以上に、リリースまでの不確実性を下げる効果があります。

## 5. 未修正時リスク

今回の論点を放置した場合、主なリスクは次の通りです。

* 実装途中で保存先不足や DTO 不足が見つかり、設計差し戻しが発生する
* Web と Mobile で permissions や状態解釈が分岐し、挙動差が出る
* 正式取り下げ、コメント非表示、再送、既読化などで二重実行バグが起きる
* 共通ヘッダーや履歴導線が画面ごとに独自実装になり、保守性が落ちる
* 検索結果や通知挙動が不安定になり、初期利用体験を損なう

これらはすべて、MVP だから後回しにしてよい種類のリスクではありません。  
むしろ MVP ほど、基礎仕様の曖昧さがそのまま品質問題として表面化します。

## 6. 推奨する進め方

推奨する進め方は、既存の slice 順を維持しつつ、今回整えた仕様を前提に着手することです。

* Slice 1 で認証、参加、共通ヘッダー依存 API を先に通す
* Slice 2 と Slice 3 で検索、投稿、レビュー、正式化を主線として成立させる
* Slice 4 と Slice 5 で改訂と Q&A を接続し、履歴導線を整える
* Slice 6 と Slice 7 で通知、管理、タグ、運用系を仕上げる

この順番なら、価値の中心である「見つける」「投稿する」「正式化する」を先に成立させつつ、後続機能のリスクも吸収しやすくなります。

## 7. 結論

今回の修正は、仕様書をきれいにしただけではありません。  
実装着手速度、正式化運用の信頼性、検索品質、参加導線、運用事故防止のすべてに効く、事業上の土台固めです。

MVP の範囲を削らずに進める前提でも、今回の整合化によって「作り始められる状態」へ近づけています。  
この状態で着手することが、開発コストと後戻りコストの両方を最も抑えられる進め方です。
