# 1. ドキュメントの目的

本ドキュメントは、MVPに必要な画面を洗い出し、各画面の役割・表示要素・操作・権限制御を定義する。

目的は次の3つ。

1. 必要画面を漏れなく定義する
2. 画面ごとの責務を明確にする
3. API設計や実装分担の前提を固定する

---

# 2. 画面設計の基本方針

## 2-1. 主役はナレッジ

トップ導線は質問ではなく、**検索可能なナレッジ一覧**を中心に置く。

## 2-2. 一覧は軽く、詳細で深く見る

一覧画面は判断材料だけを出し、編集や複雑な運用は詳細画面に寄せる。

## 2-3. 処理キューは通知ではなくバッジ

レビュー待ちは個別通知ではなく、**件数バッジ + 専用一覧**で扱う。

## 2-4. Q&Aは固定、ナレッジは育てる

質問詳細では「確定前」と「確定後」を分ける。
ナレッジ詳細では「現在版」と「履歴」を分ける。

## 2-5. 他人本文は編集させない

画面上でも、管理者やオーナーに**他人本文編集UIを出さない**。

## 2-6. Web と Mobile の差分方針

画面責務、状態遷移、API contract は Web / Mobile で共通とする。

差分を許容するのは次のみ。

* routing 実装
* navigation UI
* OS 標準の戻る導線
* file picker / share sheet など platform 固有 UI

画面名、screen ID、主要 UI セクション、呼び出し API は両 platform で揃える。

# 4. 画面共通UI

## 4-1. 共通ヘッダー

全ログイン後画面に表示。

表示要素

* サービス名
* ワークスペース名
* 検索導線
* 通知アイコン + 未読バッジ
* レビュー待ちバッジ（reviewer/admin/ownerのみ）
* ユーザーメニュー

依存API

* `GET /api/workspaces/current`
* `GET /api/notifications/unread-count`
* `GET /api/review-queue/count`（reviewer / admin / owner のみ）

## 4-2. 共通ナビゲーション

最低限の主要導線として次を置く。

* ナレッジ
* 質問
* ブックマーク
* 通知
* 管理（権限者のみ）

## 4-3. 共通バッジ

各所で以下を表示する。

* 正式
* 未レビュー
* 差し戻し
* Q&A由来
* アーカイブ済み
* 解決済み
* 再オープン中
* 編集済み（コメント）
* 直前の正式版あり

## 4-4. 共通画面状態

全 screen で最低限次の状態を実装対象に含める。

* loading: skeleton または spinner を表示し、二重送信を防止する
* empty: 初期データ 0 件時の説明文と次操作導線を出す
* error: retry 導線付きの error 表示を出す
* permission_denied: 権限不足時は操作ボタンを出さず、必要なら専用メッセージを表示する

一覧画面では `loading / empty / error` を必須、
詳細画面では `loading / error / permission_denied` を必須とする。

## 7-2. 質問詳細画面

### 目的

質問と回答を確認し、ベストアンサー選定、再オープン、ナレッジ化を行う。

### 表示要素

* タイトル
* 状態バッジ

* 関連リンク
* コメント
* 派生ナレッジ一覧
* ブックマーク
* 履歴導線
* 質問履歴一覧
* 回答履歴導線

### 回答表示

**セクションを分ける。**

#### A. 確定時点の回答

* ベストアンサー
* その時点までの他回答
* すべて凍結済み

#### B. 確定後の追記回答

* コメント
* Q&Aからナレッジ作成

* 質問本体の履歴は `GET /api/questions/{questionId}/revisions` を使う
* 各回答の履歴は `GET /api/answers/{answerId}/revisions` を使う

# 12. 画面設計上の注意点

## 12-1. resolved_locked の見せ方

「解決済みなのに回答が増えている」混乱を避けるため、
**確定前回答** と **確定後追記回答** を明確に分ける。

## 12-2. formal と編集下書きの見せ方

正式版を壊さない。
編集中の案は別導線に分離し、「現在の正式版」と混ぜない。

## 12-3. アーカイブ済み表示

アーカイブ済みコンテンツは、通常一覧では除外しつつ、
詳細では理由が見えるようにする。

## 12-4. 他人本文編集UIを出さない

admin / owner にも、他人本文の編集ボタンを出さない。

## 12-5. レビュー待ちの意味を明確にする

レビュー待ちは通知ではなく、**処理キュー**として扱う。
そのため、レビュー待ち一覧への導線を常に見える場所に置く。
