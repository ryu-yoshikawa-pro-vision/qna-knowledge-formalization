## 優先される定義

* table 名、column 名、constraint、index はこの文書を正とする
* 業務ルールや state machine 自体は `業務仕様書.md` と `状態遷移仕様.md` を優先する
* auth infrastructure の framework 実装詳細はこの文書の対象外とする

---

前提:

* DB は **PostgreSQL**
* 主キーは基本 `UUID`
* 日時は `TIMESTAMPTZ`
* リッチ本文は

  * `content_json` = ブロックエディタ正本
  * `content_markdown` = 表示/比較用派生
* enum は PostgreSQL enum でも text + check でもよいが、ここでは**enum論理名**で記載
* polymorphic 関連 (`comments`, `content_links`, `bookmarks`, `notifications`) は、DB外部キーではなく**アプリケーション側整合性保証**を前提にする

# 3. 補足ルール

## 3-1. ポリモーフィック参照の扱い

以下は DB FK ではなく、アプリ層で整合性を保証する。

* comments.content_type + content_id
* content_links.source/target
* bookmarks.content_type + content_id
* notifications.target_type + target_id

理由:

* テーブルを分けるよりMVPでは柔軟で実装しやすい
* ただし削除・アーカイブ時の整合性はアプリ側で責任を持つ

## 3-2. searchable_text / search_vector の生成

保存時に、次を連結して生成する想定。

### knowledge_items

* title
* summary
* content_markdown
* context_text
* tag names

### questions

* title
* content_markdown
* accepted_answer_snapshot_markdown
* tag names

### answers

* content_markdown

### knowledge_edit_drafts

* title
* summary
* content_markdown
* context_text
* tag names

補足:

* `searchable_text` はアプリ側で正規化した検索元文字列を保存する
* `search_vector` は保存・更新時に `searchable_text` から生成する
* 検索 API は `search_vector` を使い、`searchable_text` はデバッグ・再生成・比較用に残す

## 3-3. revision 作成タイミング

* create 時に revision 1 を作る
* update 毎に新規 revision を作る
* locked / applied / discarded 後は対象に応じて新規 revision 作成不可

## 3-4. lifecycle と参照 API の見方

* `users`, `user_sessions`, `workspaces`, `workspace_members` は auth / participation の起点
* `workspace_invitations`, `workspace_join_requests` は membership flow の状態管理
* `knowledge_items`, `knowledge_reviews`, `knowledge_edit_drafts`, `knowledge_edit_draft_reviews`, `questions`, `answers` は主要業務 table
* `*_revisions` は履歴専用で append-only
* `comments`, `content_links`, `bookmarks`, `notifications` は cross-cutting table
* 各 screen と API の参照関係は `画面APIデータ対応表.md` を正とする
