Keep the same design system, spacing, typography, color rules, status badge rules, layout structure, component language, and enterprise SaaS tone established in previous screens.

This product is knowledge-first, state-driven, role-aware, and operationally clear.
Knowledge has higher visual priority than Q&A.
Avoid social or community-platform styling.
Do not introduce playful UI patterns, engagement mechanics, or decorative visual trends.
Use a calm blue-based enterprise interface with strong readability and structured information hierarchy.

Design the Knowledge Edit screen for editing a user's own non-formal knowledge item.

Goal:
Support revision of an existing knowledge item while keeping workflow state and review context explicit.

Layout:
- Global app shell
- Page title and current item title context
- Persistent status area near the top
- Main structured editor area
- Action area separated from the writing space

Required fields:
- Title
- Summary
- Long-form body editor
- Result type selector
- Context field
- Tag input
- Visibility selector
- Draft visibility selector

Required workflow context:
- Current status
- Change request reasons if the item is in changes-requested state
- Clear indication if editing will move the item back to shared state from under review

Required actions:
- Save Draft
- Share
- Request Review

Design emphasis:
- Focused writing experience
- Strong visibility of workflow state
- Calm support for revision and resubmission
