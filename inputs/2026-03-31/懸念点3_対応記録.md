# 懸念点3 対応記録

## 1. create 系 API の auth 明記

### 判定

対応

### 理由

`auth を endpoint 節で省略した場合の既定ルール` は追加済みだが、`POST /api/workspaces/current/join-requests`、`POST /api/knowledges`、`POST /api/questions`、`POST /api/comments` は画面遷移や対象 content 条件と結び付くため、local `### auth` を明記した方が実装判断の余地を残さない。

### 反映先

* `docs/spec/API概要設計書.md`

### 採用しなかった提案

* なし

## 2. inline permissions DTO の中央集約

### 判定

対応

### 理由

`GET /api/knowledges/{knowledgeId}` と `GET /api/questions/{questionId}` にだけ inline JSON を残すと、`23-2. 共通 payload` 側と二重管理になり drift の原因になる。permissions DTO は中央定義を正本にし、各 endpoint は参照だけに寄せる方が整合的。

### 反映先

* `docs/spec/API概要設計書.md`
* `docs/spec/用語・正規一覧.md`

### 採用しなかった提案

* DTO 詳細を endpoint ごとに重複記載する案は不採用。正本を `23-2. 共通 payload` に一本化した。

## 3. payload 補完

### 判定

対応

### 理由

`admin.tags`、`bookmark.list`、`knowledge.detail`、`question.detail` の表示要件に対して、既存 payload には不足があった。必要な field は DTO 側へ追加したうえで、画面トレーサビリティにも反映した。

### 反映先

* `docs/spec/API概要設計書.md`
* `docs/spec/画面APIデータ対応表.md`
* `docs/spec/用語・正規一覧.md`

### 採用しなかった提案

* `can_bookmark` は追加しない。bookmark の不足は permission ではなく current state の不足なので、`knowledge detail.viewer.is_bookmarked` と `question detail.viewer.is_bookmarked` を追加して解消した。
* `can_change_draft_visibility` は追加しない。今回の仕様では `can_edit`、対象 status、専用 endpoint の存在で十分に判定できる。
* `sample_contents` のための admin 専用 DTO や query parameter 追加は行わない。`tag item.sample_contents[]` の lightweight preview で閉じる。

## 4. `確認事項.md` reopen

### 判定

対応不要

### 理由

`docs/spec/README.md` と `docs/spec/確認事項.md` の運用ルールでは、source から決められるものは各仕様書へ吸収し、未解決の open item だけを `確認事項.md` に残す。今回の懸念は仕様書内で閉じられるため reopen しない。

### 反映先

* `docs/spec/確認事項.md` は変更なし

### 採用しなかった提案

* 一時的に reopen してから close へ戻す案は不採用。運用ルールに反し、差分だけが増えるため。
