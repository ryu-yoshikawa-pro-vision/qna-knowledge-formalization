# 懸念点2 対応記録

## 1. API contract が未完成

- 判定: 対応
- 理由:
  - `API概要設計書.md` に local `response` 未記載 endpoint が多数残っており、そのままでは client / backend 実装者が独自 DTO を作る余地があった
  - `PATCH` 系 request も未定義が残っていたため、実装判断を排除できていなかった
- 反映先:
  - `docs/spec/API概要設計書.md`
    - `2-4. レスポンス contract を固定する`
    - `# 23. contract 補完`
- 採用しなかった提案:
  - glossary 側へ DTO field 詳細まで複製する案は対応不要
  - 理由: DTO field の正本が複数になると drift の起点になるため、field 詳細は `API概要設計書.md` に集約した

## 2. auth の省略ルールが文書化されていない

- 判定: 対応
- 理由:
  - 既存の `auth 未記載 = active member` 既定は `GET /api/auth/me`、`GET /api/workspace-resolution`、`POST /api/workspaces/current/join-requests`、`POST /api/workspace-join-requests/{joinRequestId}/cancel` に適合せず、誤実装を誘発していた
- 反映先:
  - `docs/spec/API概要設計書.md`
    - `3-4. auth を endpoint 節で省略した場合の既定ルール`
    - `2-5. endpoint 記述の補完規則`
- 採用しなかった提案:
  - すべての endpoint に個別 `### auth` を追加する案は対応不要
  - 理由: 文書量に対して保守負荷が高く、既定ルールで十分に閉じられるため

## 3. join request の path parameter が `{id}` のまま

- 判定: 対応
- 理由:
  - `{id}` は invitation / tag / knowledge などの他リソースと区別できず、contract / client / backend の naming drift を生みやすい
- 反映先:
  - `docs/spec/API概要設計書.md`
  - `docs/spec/用語・正規一覧.md`
  - `docs/spec/テーブル定義.md`
  - `docs/spec/バリデーション・業務ルール一覧.md`
  - `docs/spec/画面APIデータ対応表.md`
  - `docs/spec/画面仕様書.md`
- 採用しなかった提案:
  - `{id}` を join request だけ例外許容する案は対応不要
  - 理由: parameter naming の例外を作る合理性がなく、用語正規の方針とも衝突するため

## 4. member 管理 API の通知記述が enum / target_type と噛み合っていない

- 判定: 対応
- 理由:
  - `notification_type` / `notification_target_type` には member role change / owner transfer / member remove 用の値がなく、現行のままでは通知仕様が閉じない
  - MVP では通知を増やすより、監査ログへ寄せた方が既存方針と整合する
- 反映先:
  - `docs/spec/API概要設計書.md`
    - `# 22. endpoint 補完マトリクス`
  - `docs/spec/画面APIデータ対応表.md`
- 採用しなかった提案:
  - member 管理通知 enum / target_type を新設する案は対応不要
  - 理由: product scope 拡張になり、MVP の通知方針とも一致しないため
  - `POST /api/workspaces/current/owner-transfer` を単数 `membership` 返却にする案は対応不要
  - 理由: 実際には旧 owner と新 owner の 2 membership が更新されるため、`data.owner_transfer.previous_owner_membership` と `data.owner_transfer.current_owner_membership` に補正した

## 結論

- 4 懸念はすべて `対応`
- 追加の open item は残らなかったため、`docs/spec/確認事項.md` は `現時点の確認事項なし` を維持する
