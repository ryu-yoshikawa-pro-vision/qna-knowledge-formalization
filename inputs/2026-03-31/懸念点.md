## A. 致命的な矛盾・欠落

1. **auth/session のDB仕様が欠けています。**
   `実装前提・技術基準.md` と `実装技術一覧.md` では、Web の session と Mobile の refresh token を DB 管理する前提です。
   しかし `テーブル定義.md` に `user_sessions` 相当のテーブルがありません。
   さらに `API概要設計書.md` の endpoint 補完表では `user_sessions` と `user_profiles` が出てきます。
   **前提とDBが一致していません。**

2. **`user_profiles` がAPI設計に出るのに、DB定義にありません。**
   これも handoff としては不完全です。
   「別システムで持つ」のか「このプロダクトで持つ」のかが未確定です。

3. **検索仕様が技術的に未完成です。**
   `テーブル定義.md` では `searchable_text: TEXT` に対して `GIN full-text index` と書かれています。
   一方 `実装技術一覧.md` では `tsvector または同等` とあります。
   PostgreSQL FTS としては、このままだと**実装方法が確定していません**。

4. **`revoke-formal` の遷移先が文書間で矛盾しています。**
   多くの文書では「正式取り下げ = `formal -> shared`」です。
   しかし `API概要設計書.md` の endpoint 補完表では `formal -> archived` になっています。
   **これはそのままでは実装不能です。**

5. **コメント非表示の権限定義が矛盾しています。**
   `API概要設計書.md` の本文節と `バリデーション・業務ルール一覧.md` と `権限マトリクス.md` では「owner/admin のみ」。
   しかし `API概要設計書.md` の endpoint 補完表では「owner/admin または本人」。
   **誰が hide できるのかが統一されていません。**

6. **コメント編集の副作用 `is_edited = true` がDBに存在しません。**
   `API概要設計書.md` では `PATCH /api/comments/{commentId}` の副作用として `is_edited = true` が定義されています。
   しかし `comments` テーブルにその列がありません。
   UI では `編集済み` 表示を出す前提なので、**仕様が閉じていません。**

7. **参加申請コメントの保存先がありません。**
   `POST /api/workspaces/current/join-requests` の request に `comment` があります。
   画面でも参加申請コメントを扱う前提です。
   しかし `workspace_join_requests` には `review_comment` しかなく、申請者コメント用の列がありません。
   **データが置けません。**

8. **参加申請取消の membership log action が enum にありません。**
   `状態遷移仕様.md` では `pending -> cancelled` で membership log 作成と書いてあります。
   でも `membership_log_action` に `join_cancelled` 相当がありません。
   **状態遷移と enum が噛み合っていません。**

9. **エラーコードが統一されていません。**
   `UNAUTHORIZED` と `UNAUTHENTICATED` が混在しています。
   これは frontend 実装、共通エラーハンドリング、テストコードで確実に事故ります。

10. **endpoint 表記がブレています。**
    `PATCH /api/knowledges/{knowledgeId}` と `PATCH /api/knowledges/{id}` が混在しています。
    小さいようで、contract-first 前提ではこういうブレが無駄な迷いを生みます。

## B. 仕様として未定義・曖昧な点

11. **API response schema がかなり不足しています。**
    ざっと見ると API 概要設計書は 80 前後の endpoint があるのに、**明示的 response を持つ節は半数未満**です。
    「用途」しかない endpoint が多く、unknown 実装者には厳しいです。

12. **`GET /api/workspaces/current` が実質未定義です。**
    用途しかなく、response shape がありません。
    しかし全画面共通の workspace 情報に関わるので、ここが曖昧なのはまずいです。

13. **`GET /api/notifications/unread-count` も実質未定義です。**
    共通ヘッダーの未読バッジに必要なのに、response がありません。

14. **共通ヘッダー依存のAPIが画面API対応表で十分に追えていません。**
    `画面仕様書.md` の共通ヘッダーには workspace 名、通知未読、レビュー待ちバッジがあります。
    しかし `画面APIデータ対応表.md` では `GET /api/workspaces/current` や `GET /api/notifications/unread-count` の扱いが抜けています。

15. **Q&A の履歴機能がUI仕様として閉じていません。**
    API には `GET /api/questions/{questionId}/revisions` と `GET /api/answers/{answerId}/revisions` があります。
    しかし画面仕様として明示的にあるのはナレッジ履歴画面だけです。
    「履歴導線」は書いてあるが、**どの画面で何を見せるのかが未定義**です。

16. **knowledge 作成時の状態決定が曖昧です。**
    画面仕様は「保存 / 共有 / レビュー申請」ボタンを持っています。
    でも `POST /api/knowledges` の request には、その action を示すフィールドがありません。
    endpoint 補完表では初期状態が `draft` または `shared` とだけ書かれていて、**どの入力でどう決まるかが不明**です。

17. **permissions の response shape が定義されていません。**
    knowledge detail / question detail に `permissions` を含める前提ですが、
    具体的にどの boolean を返すのかがありません。
    これを放置すると Web と Mobile で別実装になります。

18. **`membership_status` の語彙が揃っていません。**
    `GET /api/workspace-resolution` の例では `membership_status: "none"` が出ます。
    一方 `workspace_members.membership_status` は `active / removed` です。
    「resolution用の擬似状態」なのか「DB状態」なのかが曖昧です。

19. **idempotency / 再送 / 二重実行耐性が未定義です。**
    招待受諾、join 承認、再送、apply、accept-answer、bookmark など、
    二重送信やリトライで壊れやすい操作が多いのに、再実行時の扱いが統一されていません。

20. **同時編集・競合制御が未定義です。**
    Web と Mobile の両対応なのに、version / ETag / optimistic lock などの記述がありません。
    特に comment、knowledge、question で競合処理が曖昧です。

21. **notification の重複抑止ルールがありません。**
    通知タイプは豊富ですが、再送・再実行・同一イベント多重発火をどう抑えるかが未定義です。
    このままだと通知が簡単に汚れます。

22. **招待通知の扱いが曖昧です。**
    enum に `invitation_received` はあります。
    しかし業務仕様上、招待は transactional email で飛ばす前提です。
    未参加ユーザーにアプリ内通知をどう届けるのかが不明です。

23. **タグ統合後の検索仕様が曖昧です。**
    「旧タグ検索でも target 結果を返す」は書かれています。
    でも search API は `tag_ids[]` ベースです。
    **旧タグID指定でも alias するのか、名前検索だけなのか**が明確ではありません。

24. **ポリモーフィック関連の整合性をアプリ責務に寄せすぎています。**
    `comments`, `content_links`, `bookmarks`, `notifications` は DB FK ではなくアプリ整合性前提です。
    それ自体は方針としてありですが、削除時や archive 時の cascade ルールが細かく決まっていません。

25. **監査ログの粒度が足りません。**
    状態遷移仕様では「理由記録」「ログを残す」と書いてある箇所がありますが、
    operation log のような横断監査モデルはありません。
    MVPなら削ってもいいですが、今の書き方だと**あるように見えて実はない**です。

## C. 現実性の懸念

26. **Mobile editor 方針が危険です。**
    Web は Tiptap、Mobile は markdown-first + `content_json` 変換。
    ここは往復変換で壊れやすいです。
    仕様として変換ルールが足りず、**短期MVPで一番事故りやすい箇所**です。

27. **日本語検索の品質を軽視しています。**
    PostgreSQL FTS だけで日本語中心の検索品質を満たすのかが書かれていません。
    MVPとして割り切るなら、その割り切りを明記すべきです。

28. **1 domain = 1 workspace の運用現実が甘いです。**
    大企業や Google Workspace の alias / secondary domain / subdomain をどう扱うかがありません。
    ルールとしてはシンプルですが、現実の組織運用では崩れやすいです。

29. **レビュー統制が弱いです。**
    正式化条件は「投稿者以外の有効 review が1件以上」。
    これだと admin がレビューして admin が正式化するなど、運用上の牽制が弱いままです。
    意図的に緩くしているなら明記が必要です。

30. **通知・コメント・リンク・ブックマークまでMVPに入れていて、MVPとしては重いです。**
    仕様としては成立していますが、開発体制が細いなら現実的ではありません。
    「MVP」という言葉に対して、実態はかなり広いです。

## D. 受け入れ・テスト・handoff上の懸念

31. **受け入れ基準の網羅性が足りません。**
    7シナリオ＋横断 acceptance だけでは、
    owner transfer、member remove、comment hide、質問/回答履歴、logout/refresh、二重送信などが薄いです。

32. **画面APIデータ対応表に抜けがあります。**
    API設計書にある endpoint のうち、少なくとも
    `GET /api/workspaces/current`
    `GET /api/notifications/unread-count`
    `GET /api/questions/{questionId}/revisions`
    `GET /api/answers/{answerId}/revisions`
    `POST /api/auth/logout`
    `POST /api/auth/refresh`
    などが十分に対応付けられていません。
    これはトレーサビリティ不足です。

33. **`確認事項.md` が空なのは不自然です。**
    今の仕様群には open item が明らかに残っています。
    それなのに「現時点の確認事項なし」は、整理が完了したのではなく、**未整理の論点を見ないことにしているだけ**です。

---

## まとめ

要するに、この仕様は

* **思想・業務ルール・状態遷移・権限の骨格は良い**
* でも
* **契約・DB・共通API・横断仕様の詰めが甘い**
* そして
* **“確認事項なし” と言える段階では全くない**

です。

優先度順に潰すべきなのは、まずこの5つです。

1. auth/session/user_profiles のDB仕様確定
2. `revoke-formal` と comment hide 権限の矛盾解消
3. search 実装方式の確定
4. response DTO と permissions shape の固定
5. 参加申請コメント・comment edited・membership log enum の schema 修正
