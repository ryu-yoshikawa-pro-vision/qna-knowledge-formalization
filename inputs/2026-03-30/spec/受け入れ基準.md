# 受け入れ基準

## 1. 目的

この文書は、実装完了を**ユーザーストーリー単位**で判定するための acceptance criteria である。

## 2. Scenario 1: 初回ログインから workspace 作成

### Given

* Google login できる未参加ユーザー
* 同一ドメインに workspace が存在しない

### When

* ログインする
* workspace resolution を開く
* workspace 名を入力して作成する

### Then

* user が作成または更新される
* workspace が 1 件作成される
* creator は `owner` になる
* knowledge list へ遷移できる

## 3. Scenario 2: 招待、再送、受諾

### Given

* owner または admin が存在する
* 招待対象ユーザーのメールは同一ドメイン

### When

* 招待を作成する
* 必要なら招待を再送する
* 招待対象ユーザーが token から preview を確認する
* 招待対象ユーザーが token から受諾する

### Then

* pending 招待は 1 件に保たれる
* 再送時は旧 pending が `revoked` になる
* 新 token / 新 expiry の招待が発行される
* preview で workspace 名、招待メール、role、expiry、status が確認できる
* 受諾後に workspace member が作成される

## 4. Scenario 3: 直接投稿 knowledge の review / formalize

### Given

* workspace member がいる
* reviewer / admin / owner がいる

### When

* member が knowledge を作成する
* shared にする
* review request を出す
* reviewer が review する
* admin / owner が formalize する

### Then

* status が `draft -> shared -> review_requested -> formal` と遷移する
* formalize 前に有効レビューが 1 件以上ある
* formalize 後は default search の対象になる

## 5. Scenario 4: formal knowledge の edit draft 作成から apply

### Given

* formal knowledge が存在する
* 元作成者本人がログインしている

### When

* edit draft を作成する
* edit draft を更新し review request する
* reviewer が review する
* admin / owner が apply する

### Then

* 未完了 edit draft は 1 件に保たれる
* `knowledge_edit_draft_reviews` が記録される
* apply 時に `knowledge_items` の同一 ID が更新される
* 旧正式版は `knowledge_revisions` に保存される

## 6. Scenario 5: 質問、回答、ベストアンサー、再オープン

### Given

* workspace member が質問を閲覧できる

### When

* question を作成する
* answer を複数付ける
* 質問投稿者または admin / owner が best answer を選ぶ
* その後 reopen する

### Then

* question は `open -> resolved_locked -> open` と遷移する
* accepted answer snapshot が保存される
* lock 済み回答は reopen 後も解凍されない

## 7. Scenario 6: Q&A から knowledge 作成

### Given

* 閲覧可能な question が存在する

### When

* question detail から knowledge 化を実行する

### Then

* draft knowledge が作成される
* `source_type = qa_derived`
* `source_question_id` が設定される
* best answer があれば初期本文に反映される

## 8. Scenario 7: タグ統合、検索、通知、レビュー待ちバッジ

### Given

* tag が複数存在する
* review_requested の knowledge / edit draft が存在する

### When

* owner / admin が tag を統合する
* knowledge search を実行する
* reviewer / admin / owner が header を見る

### Then

* old tag は `merged` になる
* 既存 content への tag 紐付けが target に寄る
* old tag 検索でも target 結果が返る
* review queue badge が `review_requested` 件数を反映する

## 9. 横断 acceptance

すべての scenario で次を満たすこと。

* visibility を満たさない画面や API は `FORBIDDEN` になる
* 他人本文編集は常に禁止される
* revision 対象 entity は create と update で履歴が残る
* archive 理由、discard 理由、delete 理由の必須条件が守られる
* screen / API / table / status / permission が `画面APIデータ対応表.md` と一致する
