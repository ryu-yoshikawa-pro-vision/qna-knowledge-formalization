# 懸念点4 対応記録

## 1. `knowledge permissions DTO` への `can_change_draft_visibility` 追加

### 判定

対応

### 理由

通常 knowledge には `POST /api/knowledges/{knowledgeId}/draft-visibility` が存在し、画面仕様にも `draft_visibility` 切替がある。permissions DTO にその可否が無いと、UI 制御の根拠が endpoint と画面仕様に分散したまま残る。

### 反映先

* `docs/spec/API概要設計書.md`
* `docs/spec/権限マトリクス.md`
* `docs/spec/用語・正規一覧.md`

### 採用しなかった提案

* なし

## 2. `knowledge edit draft permissions DTO` への `can_change_draft_visibility` 追加

### 判定

対応

### 理由

正式ナレッジ編集下書きには `POST /api/knowledge-edit-drafts/{draftId}/draft-visibility` と画面上の切替操作がある。DTO に field が無いままだと、通常 knowledge と編集下書きで contract の粒度が揃わない。

### 反映先

* `docs/spec/API概要設計書.md`
* `docs/spec/用語・正規一覧.md`

### 採用しなかった提案

* なし

## 3. `question permissions DTO` への `can_bookmark` 追加

### 判定

対応不要

### 理由

bookmark は detail 画面だけでなく一覧 UI にもまたがる cross-cutting 操作であり、現在の contract は `POST /api/bookmarks` / `DELETE /api/bookmarks` と `viewer.is_bookmarked` で閉じている。question detail だけに `can_bookmark` を足しても、一覧系の判断軸は増えず、契約が二重化するだけになる。

### 反映先

* 変更なし

### 採用しなかった提案

* `question permissions DTO` に `can_bookmark` を追加する案は不採用。bookmark の handoff は current state と mutation API で扱う。

## 4. `knowledge permissions DTO` への `can_bookmark` 追加

### 判定

対応不要

### 理由

knowledge でも bookmark は一覧と詳細の両方で使うため、detail permissions への追加だけではモデルが閉じない。既に `knowledge list item` と `knowledge detail` の両方に `viewer.is_bookmarked` があり、bookmark API も独立しているため、permissions field は不要。

### 反映先

* 変更なし

### 採用しなかった提案

* `knowledge permissions DTO` に `can_bookmark` を追加する案は不採用。`viewer.is_bookmarked` を維持する。

## 5. glossary への `can_change_draft_visibility` 追加

### 判定

対応

### 理由

`用語・正規一覧.md` は permissions field の中央台帳であり、`API概要設計書.md` で使う field は同じ正規名で列挙する必要がある。`can_change_draft_visibility` を追加しないと、台帳と contract が再びずれる。

### 反映先

* `docs/spec/用語・正規一覧.md`

### 採用しなかった提案

* なし

## 6. glossary への `can_bookmark` 追加

### 判定

対応不要

### 理由

spec 本体で `can_bookmark` を採らない以上、中央台帳にも追加しない。ここだけ先行して追加すると、存在しない field を正規名として承認した状態になる。

### 反映先

* 変更なし

### 採用しなかった提案

* `can_bookmark` を正規名に追加する案は不採用。

## 7. `確認事項.md` reopen

### 判定

対応不要

### 理由

`README.md` と `確認事項.md` の運用ルールでは、source から決められるものは各仕様書へ吸収し、open item だけを `確認事項.md` に残す。今回の論点は spec 内で判断可能なので reopen しない。

### 反映先

* `docs/spec/確認事項.md` は変更なし

### 採用しなかった提案

* 一時 reopen してから close へ戻す案は不採用。運用ルールと衝突する。

## 8. 「3ファイルだけ修正」方針

### 判定

対応不要

### 理由

`can_change_draft_visibility` を DTO に追加するなら、その根拠である権限制御の source of truth も揃える必要がある。`権限マトリクス.md` を更新しないまま 3 ファイルで閉じると、permissions DTO だけが先行して再び整合が崩れる。

### 反映先

* `docs/spec/権限マトリクス.md`

### 採用しなかった提案

* `API概要設計書.md`、`用語・正規一覧.md`、`確認事項.md` の 3 ファイルだけで完結させる案は不採用。
